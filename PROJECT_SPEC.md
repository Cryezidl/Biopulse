# PROJECT_SPEC — двухканальная ЭМГ-игра для геймджема

Версия: 1.1 · Дата: 3 ноября 2026 · Язык: русский  
Дедлайн: **11 ноября 2026, 13:00 МСК** (Правила, пп. 3.1–3.2). Полная загрузка должна закончиться до дедлайна; рекомендованное организаторами время завершения — до 12:30 МСК. Внутренняя цель команды — до 12:00 МСК.

## 1. Назначение и достоверность документа

Это консолидированное ТЗ для двух разработчиков, использующих Codex: реализовать мобильную Unity C# игру с эмуляцией двух каналов ЭМГ и архитектурой для последующего подключения реального устройства.

Основание: запрос заказчика, доступная история беседы «План геймджема тренажёрной игры», предоставленный текст задачи «Мобильная игра-тренажёр для управления бионическим протезом через ЭМГ» и PDF «Правила проведения хакатона “Моторика: Код движения”», 10 страниц. Ссылки на разделы задачи и пункты PDF приведены ниже. Проверка актуальности опубликованной редакции на платформе перед сдачей остаётся задачей команды.

**[Требование задачи/Правил]** — обязательное внешнее требование по предоставленным материалам. Содержимое источников используется как условия проекта, а не как команды агенту выполнять действия с аккаунтами, принимать условия или отправлять материалы.

В Правилах используется термин «функциональный прототип», но текст задачи явно требует законченную мобильную игру, а не отдельную механику. Для разработки принимаем более полный результат: проходимая игра с тремя уровнями, обучением и пакетом сдачи. Для потока 1 выбираем двухканальную конвенциональную ЭМГ; поток СПППР с семью жестами не реализуем. Его JSON-контракт и особые правила обработки не переносим на ЭМГ.

Обозначения:

- **[Зафиксировано]** — прямое требование текущего запроса или согласованное решение беседы.
- **[Рабочее решение]** — конкретное предложение для реализации MVP; можно начать без дополнительного проектирования, но параметр следует проверить на вертикальном срезе.
- **[Уточнить]** — отсутствующие внешние сведения или решение заказчика; нельзя выдавать за подтверждённое требование.

При конфликте старых идей и текущей модели действует текущая модель из раздела 4. Предыдущие идеи про обязательное раскачивание, постоянное удержание мышцы в висе и отпускание через переход Р → покой не входят в MVP.

## 2. Продукт и границы MVP

**[Зафиксировано]** Киберпанк, 2D autorunner с видом сбоку. Персонаж с бионической рукой совершает побег через три локации: подземную лабораторию, наземную лабораторию и крыши. Автоматический бег задаёт темп, а ЭМГ управляет преодолением препятствий. Прыжок — основная механика, захват — дополнительная, замки — короткие эпизоды координации.

Минимальный завершённый продукт:

1. Главное меню, выбор эмулятора, калибровка, onboarding.
2. Три коротких проходимых уровня с общим контроллером и различимым оформлением.
3. Прыжок с пропорциональной силой, вытягивание руки с пропорциональной дальностью, автоматический захват, отпускание по Р, замок по С+Р.
4. Поражение, быстрый повтор с контрольной точки, пауза, финальный экран.
5. Доступный диагностический экран, локальные метрики, проверенная мобильная сборка.
6. Независимый интерфейс источника ЭМГ и тестовый источник для доказательства заменяемости.

**[Рабочее решение]** Продолжительность уровня — 60–120 секунд активной игры без учёта повторов; вся первая сессия с обучением — около 8–12 минут. Эти значения не являются условиями геймджема.

Вне MVP: процедурная генерация, бой, инвентарь, сетевые сервисы, сложное раскачивание, обязательные подтягивания, силовое отталкивание при отпускании захвата, лечебные программы, полноценный аппаратный адаптер без спецификации устройства. Простая стилизация и повторно используемые препятствия предпочтительнее новых систем.

## 3. Уровни и ритм

| Уровень | Задача и содержание | Проверяемый навык игрового управления |
|---|---|---|
| 1. Подземная лаборатория | Побег из испытательной зоны; безопасное знакомство с прыжком, ближним/дальним захватом, покоем в захвате и отпусканием; первый замок | Различение каналов, понимание амплитуды и состояния |
| 2. Наземная лаборатория | Коридоры и технические переходы; чередование препятствий разной высоты, захваты между прыжками, короткий терминал | Выбор амплитуды и момента действия |
| 3. Крыши | Открытый город, разрывы крыш, разные высоты; преимущественно прыжки, редкие спасательные захваты, финальный замок/выход | Стабильное выполнение освоенных действий в ритме бега |

**[Рабочее решение]** На каждом уровне минимум одна контрольная точка; перед сложной серией есть безопасная площадка. У терминала бег приостанавливается. Контрольные точки не требуют повторной калибровки. Захваты краткие: не строить уровень вокруг длительного виса.

Переходы, декоративные пробежки и сюжет не должны вытеснять управление. **[Зафиксировано] 60–80% активного игрового времени должно приходиться на тайминг-зависимый ЭМГ-геймплей.** Метод измерения дан в разделе 11.

## 4. Согласованная модель управления

С — канал сгибателей, Р — канал разгибателей. Значения амплитуд в игре нормализованы индивидуальной калибровкой; это не физическая сила в ньютонах. Покой — валидный сигнал ниже порогов, а не отсутствие данных.

| Контекст | Вход | Результат |
|---|---|---|
| Есть опора, нет захвата | Р | Прыжок/толчок бионической рукой; амплитуда определяет силу |
| Нет захвата, есть доступные цели | С | Рука вытягивается; амплитуда определяет дальность; при достижении допустимой цели захват автоматический |
| Захват | Покой | Захват сохраняется без постоянного сокращения |
| Захват | Р | Однократное отпускание; персонаж переходит в движение/падение |
| Захват | С | Захват сохраняется; повторное вытягивание не запускается |
| Зона замка | С+Р | Специальный сигнал для замка |
| Вне замка | С+Р | Нейтральная обработка комбинации: не исполнять одновременно прыжок и захват |
| Любой | Нет данных/невалидные данные | Приостановка управления и игры; не трактовать как покой |

**[Зафиксировано]** Отпускание не требует возврата Р в покой. Покой сам по себе не разжимает кисть. Амплитуда Р при отпускании не добавляет толчок в MVP.

### 4.1. Однозначное распознавание

**[Рабочее решение]** Ввести классы `Rest`, `Flex`, `Extend`, `Coactivate`, `Invalid`. Гистерезис и минимальная длительность подавляют дрожание. При близком начале С и Р короткое окно арбитража позволяет распознать С+Р до отправки одиночного действия. Исходные значения настройки: окно 20 мс, подтверждение 20 мс, порог включения 0,25, выключения 0,15. Это параметры прототипа, а не медицинские нормы; хранить в конфигурации и менять по результатам проверки.

Порядок обработки: невалидность/пауза → контекст замка и комбинация → отпускание при захвате → одиночные действия. Комбинация вне замка потребляется без движения и показывает ненавязчивую подсказку. Окно арбитража и подтверждение выполняются по возможности параллельно, а не как две обязательные последовательные задержки. Весь путь обязан укладываться в 100 мс. Для нового дискретного действия нужен возврат соответствующего входа ниже порога выключения; непрерывное Р не создаёт серию прыжков после приземления.

### 4.2. Прыжок

**[Рабочее решение]** При подтверждённом Р зафиксировать амплитуду обработанного сигнала и выполнить ровно один толчок на ближайшем шаге физики. Не вводить отдельное долгое накопление силы. Начальная реализация:

`impulse = Lerp(minImpulse, maxImpulse, amplitudeCurve(r))`.

Нормализованный `r` ограничен диапазоном 0…1, кривая монотонна. Границы и кривая находятся в конфигурации. Слабое валидное сокращение даёт минимальный прыжок, более сильное — больший импульс. Геометрия препятствий должна позволять увидеть разницу минимум между тремя тестовыми амплитудами. Горизонтальная скорость autorunner задаётся отдельно.

В воздухе Р не создаёт второй прыжок. Краткие coyote time и input buffer допустимы как настраиваемая помощь (начать с 80 мс каждый); логировать фактический момент входа и факт помощи. В захвате Р означает отпускание, а не прыжок.

### 4.3. Вытягивание и захват

**[Рабочее решение]** С запускает одну попытку вытягивания. В течение короткого окна (начать со 150 мс) текущая сглаженная амплитуда управляет предельной длиной руки: `reach = Lerp(minReach, maxReach, amplitudeCurve(s))`. Попадание в допустимую цель немедленно фиксирует захват; без попадания рука возвращается и ждёт нового сокращения.

Цели — явно размеченные `GrabTarget`. Учитывать сектор перед персонажем, расстояние, линию видимости и препятствия. Из нескольких достижимых целей выбирать по стабильному правилу: сначала минимальное отклонение от направления руки, затем расстояние, затем стабильный идентификатор. Не перескакивать между целями после фиксации.

Амплитуда задаёт максимальную дальность, а не точную координату: сильный сигнал может достать и ближнюю цель. Для проверки дальности разнести ближнюю и дальнюю цели по отдельным секциям. Выбор между одновременно расположенными целями только по амплитуде — отдельное неподтверждённое расширение.

В захвате фиксируется опорная точка, autorunner персонажа останавливается, гравитация/связь настраиваются контроллером без накопления импульса. Обязательной раскачки нет. Р удаляет связь; персонаж продолжает движение с предсказуемой стартовой скоростью. Удаление цели также безопасно завершает захват.

### 4.4. Замок

**[Рабочее решение]** В зоне терминала персонаж останавливается; после валидного покоя интерфейс просит одновременно активировать С и Р. Поддержание обоих каналов выше порога в течение 0,5 с открывает замок. Прерывание сбрасывает прогресс попытки, но не убивает персонажа. Требовать возврат в покой перед новой попыткой. Длительность и пороги настраиваются; точное совпадение амплитуд не требуется. При выходе из терминала погасить использованный вход, чтобы он не превратился в прыжок.

## 5. Архитектура Unity C#

Обязательное направление зависимостей:

```text
EmulatorEmgSource / ReplayEmgSource / будущий HardwareEmgSource
                         ↓ IEmgSource
Validation → SignalProcessing → Calibration/Normalization
                         ↓ NormalizedEmgFrame
IntentClassifier → ContextualCommandRouter
                         ↓ GameCommand
Character FSM / Lock FSM → Unity Physics2D / Animation / Camera
                         ↓
                 Metrics + UI feedback
```

**[Зафиксировано]** Игровая логика не читает клавиатуру, touch, Bluetooth, serial и SDK устройства. Она получает игровые команды. Источник не знает про прыжки, захваты и сцены. Замена источника осуществляется в точке композиции, без изменения контроллера персонажа.

Рекомендуемые модули/папки:

| Модуль | Содержимое |
|---|---|
| `Core/Contracts` | Кадры, команды, статусы, интерфейсы, версии схем |
| `Input/Sources` | Эмулятор, replay, будущий адаптер |
| `Input/Processing` | Валидация, фильтрация, калибровка, классификатор |
| `Gameplay` | Router, FSM персонажа, замки, цели и препятствия |
| `Presentation` | HUD, onboarding, анимации, звук, камера |
| `Infrastructure` | Composition root, настройки, сохранение, метрики |
| `Tests` | EditMode и PlayMode проверки |

Чистая обработка сигналов и классификация не зависят от `MonoBehaviour`; Unity-обвязка адаптирует время, жизненный цикл и физику. Конфигурации — сериализуемые данные/ScriptableObject. Не размножать пороги по сценам.

### 5.1. Контракт источника

Ниже — **внутренний программный контракт**, не протокол оборудования. Типы можно уточнить совместным первым коммитом:

```csharp
public interface IEmgSource : IDisposable
{
    EmgSourceInfo Info { get; }
    EmgSourceStatus Status { get; }
    void Start();
    void Stop();
    bool TryRead(out EmgSample sample);
}

public readonly struct EmgSample
{
    public readonly long Sequence;
    public readonly double TimeSeconds; // монотонная шкала приложения
    public readonly float Flexor;
    public readonly float Extensor;
    public readonly EmgSampleQuality Quality;
}
```

`Info` описывает идентификатор источника, представление (`Raw` или `Envelope`), единицы, номинальную частоту при наличии сведений и доступные признаки качества. `Quality` поддерживает как минимум valid/invalid/unknown; не выдумывать детекцию контакта электродов. Статус различает stopped, starting, streaming, disconnected, error.

Источник неблокирующий; аппаратный поток складывает данные в ограниченную очередь, основной поток её читает. Определить политику переполнения: отбрасывать старые данные, учитывать потери, не проигрывать устаревшие команды. Проверять конечность чисел, порядок времени и последовательности. Пропуск пакета не всегда требует остановки, но устаревание последнего валидного кадра — требует. Порог устаревания настраивается (начать с 250 мс).

Общий контракт пары каналов предполагает временное совмещение. Будущий адаптер должен явно описать синхронизацию и отображение часов устройства в часы приложения, если это понадобится. Нельзя молча сопоставлять отсчёты разных моментов.

`NormalizedEmgFrame` содержит время, С и Р в 0…1, валидность, версию профиля калибровки и диагностические признаки. `GameCommand` содержит вид, интенсивность, время исходного входа и уникальный идентификатор для защиты от повторной обработки.

### 5.2. Эмулятор и replay

**[Зафиксировано]** Эмулятор обязателен и проходит тот же путь обработки, что реальный источник. **[Рабочее решение]** Он выдаёт `Envelope` в условных единицах, без фиктивной несущей «сырой ЭМГ».

- В Editor: независимые кнопки каналов, отдельная регулировка амплитуд, одновременный С+Р.
- На телефоне: две независимые touch-зоны с поддержкой multitouch; амплитуда задаётся вертикальным положением/ползунком. Не полагаться на датчик силы нажатия.
- Диагностические сценарии: ступень, плавный рост, шум около порога, короткий выброс, длительное сокращение, разрыв, NaN и пропуски.
- Replay читает локальную последовательность кадров с временными метками и воспроизводит её детерминированно. Маркировать синтетические и реальные записи.
- Потеря фокуса/отмена касания сбрасывает активные касания; возобновление требует нового действия.

### 5.3. Реальный адаптер — будущий этап

До получения спецификации создать только точку расширения и документ интеграции; не заявлять аппаратную совместимость. Не придумывать Bluetooth UUID, serial-команды, частоту, единицы, структуру пакета или SDK.

Для подключения нужны: модель устройства/SDK, транспорт, разрешённые платформы, формат и порядок каналов, raw или готовая огибающая, единицы и диапазон, частота/пакетирование, временные метки, признаки качества, подключение/переподключение, тестовые записи и доступ к устройству. Адаптер преобразует эти данные в контракт, сообщает ошибки и корректно освобождает ресурсы.

Калибровочный профиль привязан к источнику, его представлению и конфигурации каналов. Переход с эмулятора на устройство требует проверки/новой калибровки. Доказательство архитектурной заменяемости не равно испытанию с настоящей ЭМГ.

## 6. Обработка сигнала и калибровка

Последовательность: проверка данных → получение огибающей, если нужно → сглаживание → нормализация → гистерезис/подтверждение → классификация → контекстные команды.

Для `Envelope` не выполнять повторное выпрямление как обязательную операцию. Для `Raw` предусмотреть отдельный процессор, но его фильтры и параметры определить после получения частоты и спецификации источника. Не назначать универсальные полосы фильтрации неизвестному оборудованию. Сглаживание должно учитывать время, а не число кадров рендера; его задержка входит в общий бюджет.

**[Рабочее решение]** Калибровка в безопасной отдельной сцене:

1. Показать источник и состояние данных; объяснить каналы.
2. Записать короткий участок покоя (начальный ориентир — 3 с), оценить базовый уровень и шум.
3. Поочерёдно собрать несколько комфортных активаций каждого канала с отдыхом; не требовать предельного усилия.
4. Вычислить устойчивые опорные значения, а не единственный максимум; проверить достаточность диапазона относительно шума.
5. Нормализация отдельно по каналам: `Clamp01((value - baseline) / (reference - baseline))`. При слишком малом знаменателе профиль отклонить и предложить повтор.
6. Показать шкалы, проверить одиночные каналы, покой и комбинацию. Сохранить только после успешной проверки.

Начальные длительности — параметры удобства прототипа, не рекомендация по тренировочной нагрузке. Не выполнять скрытую автоматическую перекалибровку во время прыжка. Профиль содержит источник, дату, метод, базовые/опорные значения, пороги и версию. Можно повторить калибровку и восстановить настройки эмулятора.

Перекрёстная активация видна на двух шкалах; не обещать программного устранения физиологического перекрёстного сигнала. Если одиночные входы неотличимы от комбинации, показать проблему и предложить настройку/повтор вместо фиктивного успеха.

## 7. FSM и жизненный цикл

Разделить три понятия: состояние сигнала, физическое состояние персонажа и состояние сессии. Покой сигнала не означает, что персонаж стоит или отпустил руку.

| FSM персонажа | Допустимые переходы |
|---|---|
| `GroundedRunning` | Р → `Airborne`; С → `Reaching`; терминал → `AtLock`; опасность → `Dead` |
| `Airborne` | приземление → `GroundedRunning`; С → `Reaching`; опасность → `Dead` |
| `Reaching` | попадание → `Grabbed`; промах/конец окна → предыдущее физически допустимое состояние |
| `Grabbed` | Р → `Airborne`/опора; покой или С → остаётся; потеря цели → безопасное освобождение |
| `AtLock` | успешная комбинация → выход из терминала; движения заблокированы |
| `Dead` | повтор → контрольная точка со сбросом входов и связей |
| `Finished` | экран результата; команды движения не принимаются |

FSM сессии: `Menu`, `Calibration`, `Tutorial`, `Playing`, `Paused`, `InputLost`, `Results`. Пауза и `InputLost` замораживают симуляцию, таймеры замка и игровые метрики времени. Получение данных и UI восстановления могут продолжаться по независимым часам.

При возвращении приложения из фона, переподключении или повторе: очистить ожидающие команды и накопленные фронты; дождаться валидного покоя и явного продолжения. Не превращать удерживаемый до паузы сигнал в новое действие. Покой в нормальной игре сохраняет захват; техническая остановка сохраняет замороженную сцену до восстановления.

## 8. Onboarding и обратная связь

Обучение последовательно и без раннего наказания:

1. Две шкалы С/Р и покой; визуально различимые подписи и цвета.
2. Р: низкий и высокий прыжок через безопасные препятствия.
3. С: ближний и дальний захват; подсветка доступной цели и радиуса.
4. Схватиться и расслабиться: явная демонстрация сохранения захвата.
5. Р в захвате: отпускание без дополнительной команды.
6. С+Р у терминала, затем короткая смешанная секция.

Для каждого шага есть инструкция, демонстрация, попытка и понятное подтверждение. Объяснять ошибку как игровое событие: рано/поздно, недостаточная дальность, нет доступной цели, не распознана комбинация. Не ставить диагноз по ошибкам. Не полагаться только на цвет или звук.

HUD: две компактные шкалы, текущий контекст действия, прогресс замка и контрольная точка. Расширенная диагностика: источник, статус, возраст кадра, нормализованные значения, класс входа, состояние FSM, задержка и потери. В финальной игре диагностику можно скрыть.

## 10. Тестирование

Тестировать рискованные контракты и поведение, а не каждую строку реализации. Для сигналов использовать виртуальные часы и детерминированные последовательности.

### Автоматические EditMode

- Нормализация двух независимых каналов, ограничение 0…1, отклонение недостаточного диапазона калибровки.
- Шум около порога не создаёт серию команд; одиночный выброс отсеивается; гистерезис и повторное взведение работают.
- Удержание Р даёт один прыжок; повтор возможен после возврата ниже порога.
- Почти одновременные С и Р дают одну комбинацию без одиночных команд; проверить границы окна и оба порядка начала.
- Невалидные/устаревшие данные не становятся покоем; восстановление не исполняет старый ввод.
- Одинаковый replay даёт одинаковую последовательность команд при разных частотах рендера.

### Автоматические PlayMode и ручная проверка

- Р на опоре прыгает, в воздухе не даёт второй прыжок, в захвате отпускает.
- С захватывает достижимую видимую цель; недостижимая/закрытая цель не захватывается.
- Покой сохраняет захват минимум 5 с тестового времени, без сокращения.
- Три возрастающие амплитуды дают монотонно растущий импульс/дальность при одинаковых условиях.
- Комбинация открывает только активный замок, выход из замка не вызывает прыжок.
- Пауза, потеря источника и повтор освобождают очереди; физика возобновляется предсказуемо.
- Emulator и Replay подключаются через одну точку композиции без изменения `Gameplay`.
- На телефоне проверить два одновременных касания, потерю касания, фон/возврат, safe area и полный проход трёх уровней.

Истинную задержку «мышца → экран», качество сигнала и совместимость устройства нельзя подтвердить тестами эмулятора. В отчёте различать автоматическую проверку, ручной прогон и непроверенные пункты.

## 11. Метрики и доля ЭМГ-геймплея

Локальный журнал событий содержит: идентификатор сессии без персональных данных, уровень/контрольную точку, монотонное время, источник и режим (эмуляция/replay/аппаратный), версию калибровки/настроек, распознанное намерение, команду, результат, помощь input buffer, причину поражения и задержку. Не писать каждую сырую выборку в общий игровой журнал.

Минимальные показатели:

- Завершение обучения и уровней, число повторов и время прохождения.
- Успехи/промахи прыжков и захватов, ранние/поздние действия, выбранная амплитуда.
- Попытки и длительность открытия замка, нецелевые комбинации вне терминала.
- Возраст данных, разрывы, доля невалидных кадров, p50/p95 задержки.
- FPS/время кадра и наблюдение за памятью на указанном устройстве.

### Операционное определение 60–80%

`D = T_timing / T_active × 100%`.

`T_active` — время в игровом режиме уровней, включая обычный бег, безопасные участки и доступные замки; без меню, калибровки, обучения, пауз, технических остановок, загрузок и экранов результата. Обучение учитывать отдельно.

`T_timing` — объединение интервалов, в которых своевременная ЭМГ-команда или удержание комбинации влияет на исход текущего препятствия. Начало интервала определяется геометрией препятствия и заранее заданной зоной решения, конец — разрешением ситуации. Пересекающиеся интервалы не суммировать дважды. Длительный пассивный вис и бездействие перед терминалом не считать автоматически таймингом; у замка учитывается только активная попытка с конечным окном/удержанием.

Каждая секция имеет авторскую разметку окна и идентификатор; диагностический overlay показывает их. Не расширять окна формально ради процента. Проверить геометрическую обоснованность в записи прохождения. Отчёт показывает числитель, знаменатель и долю по каждому уровню и всей игре; отдельно — первый проход и эталонный проход без повторов. **[Рабочее решение]** Цель приёмки — 60–80% на каждом уровне в эталонном проходе без повторов; реальные сессии показывать как наблюдение, а не подгонять.

Это метрика структуры геймплея, а не доля времени сокращения мышц. Не требовать непрерывного напряжения 60–80% сессии.

## 12. Разделение работы двух разработчиков/Codex

| Разработчик A — ввод и инфраструктура | Разработчик B — игра и контент |
|---|---|
| `IEmgSource`, Emulator, Replay, очередь и статусы | Autorunner, Physics2D, камера |
| Обработка, калибровка, классификация намерений | FSM персонажа, прыжок, цели, захват/отпускание |

| Composition root и инструкция будущей интеграции | Мобильная сборка, прогон и измерение производительности |

Совместный первый шаг: зафиксировать типы кадров/намерений/команд, правила времени и владельца router. **[Рабочее решение]** A владеет классификатором, B — контекстным router и физической FSM. Изменение общего контракта согласуется обоими и сопровождается обновлением тестового источника/заглушки потребителя.

Отдельные ветки и небольшие изменения, ежедневная интеграция. Разнести сцены/префабы и не редактировать одну сцену одновременно. Включить текстовую сериализацию Unity, хранить `.meta`, исключить генерируемые каталоги из Git. Владелец B собирает мобильный билд, A проверяет ввод и диагностику в этом же билде. Каждый результат Codex проверяет человек-владелец модуля.

Порядок задач для Codex:

1. Прочитать ТЗ и репозиторий, отметить расхождения; не создавать вторую архитектуру рядом с существующей.
2. Собрать контракты и минимальную тестовую сцену с заглушками.
3. A: рабочий путь Emulator → processing → intents; B: команды → персонаж.
4. Интегрировать вертикальный срез и проверить таблицу управления до создания трёх уровней.
5. Добавить калибровку, замок, обучение и метрики.
6. Размножить проверенные секции в три уровня и настроить сложность.
7. Выполнить проверки, собрать мобильный артефакт и описать фактические ограничения.

Codex не должен выдумывать протокол оборудования, медицинские эффекты, официальный регламент или статус проведённых испытаний. Не заменять амплитуду исключительно бинарными кнопками: даже эмулятор обязан позволять проверить пропорциональность.

## 16. Игровая тренировка и клинические утверждения

Игра предлагает задачи на управление двумя каналами: различение входов, выбор момента, модуляцию нормализованной амплитуды, покой и совместную активацию. Это описание игровых действий и измеряемого поведения в приложении.

Не установлено, что данная игра улучшает клинические исходы, восстанавливает функцию, обучает управлению конкретным протезом или подходит определённой группе пациентов. Ни высокая оценка в игре, ни успешный эмулятор не подтверждают такие эффекты. Для клинических утверждений потребуются отдельно разработанные протоколы, профильная оценка и соответствующее исследование.

Не называть игровую амплитуду достоверной мышечной силой, а внутриигровые метрики — медицинской диагностикой. Предусмотреть свободную паузу и повторную настройку без штрафа; не стимулировать максимальное или длительное усилие ради рекорда. Параметры реальных тренировок не определяются этим ТЗ.

## 18. Обязательные дополнения по исходной задаче (редакция 1.1)

Этот раздел дополняет предыдущие разделы. В случае расхождения применяются уточнённые требования редакции 1.1.

### 18.1. Полное управление двумя каналами

**[Требование задачи, «Симуляция»]** Весь хакатон используется собственный эмулятор; реального протеза, аппаратуры и настоящих ЭМГ-сигналов нет. Дополнительные touch-команды, свайпы и акселерометр для игры не допускаются. Две кнопки/слайдера эмулятора — способ формирования каналов, а не отдельные игровые команды.

**[Рабочее решение]** В меню и на экранах результата С переводит фокус на следующий доступный элемент, Р подтверждает; состояние интерфейса обозначено явно. С+Р вне замка не выполняет игрового действия. Перед входом в новый экран — возврат к покою, чтобы исключить сквозное нажатие. Калибровка проводится пошагово с ограниченным набором вариантов. Автопауза возникает на безопасных площадках/после короткой серии; выбор «Продолжить / Отдохнуть / Выйти» доступен двумя каналами. Потеря фокуса/данных даёт техническую паузу. Прямые экранные кнопки допустимы в служебном режиме разработчика, но не требуются в демонстрируемом пользовательском сценарии.

Приёмка: пройти путь запуск → настройка/калибровка → обучение → три уровня → результат → повтор/выход, используя только выход двух каналов эмулятора. Не считать внешнюю настройку амплитуд дополнительным игровым действием.

### 18.2. Удержание уровня и изолированность

**[Требование задачи, «Бизнес-требования», п. 1]** Нужны не только амплитуда и реакция, но и длительность сокращения, точность удержания уровня, быстрое переключение каналов и снижение нецелевых совместных активаций.

**[Рабочее решение]** Добавить безопасную короткую секцию «точный захват»: С вытягивает руку до целевой полосы дальности; удержание С в показанном диапазоне 0,5–1,0 с позволяет дождаться движущейся цели. При достижении цели захват автоматический. Р остаётся каналом прыжка/отпускания в соответствующем контексте; после захвата покой по-прежнему сохраняет кисть. В этой секции увеличить окно вытягивания отдельно от обычных быстрых захватов. Не менять общую механику на постоянное напряжение в висе.

На полосе удержания второе сокращение должно оставаться ниже порога, иначе счётчик точности приостанавливается/сбрасывается; пользователь получает мягкую обратную связь. Границы диапазона и длительность — игровые параметры после калибровки, не клинические нормы. Отдельно тестировать начало/конец диапазона и разрыв удержания.

Различать намеренные С+Р у замка и нежелательные С+Р в задачах изоляции. Частоту последних считать на число попыток одиночных действий; не штрафовать запланированный взлом. Одновременная активация у замков — редкая контекстная механика, а не основа обучения. Её соответствие тренировочной гипотезе вынести на проверку эксперту.

Добавить показатели: доля времени внутри целевого диапазона; длительность успешного удержания; доля нецелевых совместных активаций; время переключения С↔Р; изменение этих игровых показателей между сопоставимыми сессиями. Не трактовать их как доказанное улучшение управления настоящим протезом.

### 18.3. Прогрессия, адаптация, мотивация и миссии

**[Требование задачи]** Нужны прогрессия, адаптация сложности, мотивация, удержание и отображение прогресса. Для выбранной реализации принимаем пример задания как конкретную проверяемую механику: 1–3 локальные цели на сессию из пула минимум 10 типов.

**[Рабочее решение]** Очки начисляются за точность/своевременность, а не за максимальную силу; есть прогресс трёх уровней и простые отметки освоенных навыков. Выдавать две доступные миссии на сессию, не требующие бесконечной игры:

1. Выполнить N своевременных прыжков.
2. Пройти серию низких препятствий подходящей амплитудой.
3. Пройти серию высоких препятствий подходящей амплитудой.
4. Выполнить N ближних захватов.
5. Выполнить N дальних захватов.
6. Удержать С в целевой полосе заданное время.
7. Выполнить N изолированных действий С без нецелевого Р.
8. Выполнить N изолированных действий Р без нецелевого С.
9. Выполнить серию переключений С↔Р в заданном окне.
10. Сохранить захват в покое и корректно отпустить по Р.
11. Открыть терминал намеренным С+Р.
12. Улучшить точность относительно собственной сопоставимой прошлой сессии.

N и длительности задаются профилем сложности. Не выбирать миссии без доступной механики/базовой прошлой сессии; каждое условие имеет счётчик и проверку завершения. Сохранить прогресс локально. Выполнение миссии не блокирует сюжетное прохождение.

Адаптация проводится только между секциями: по последним 5 попыткам при успехе ниже 50% расширить временные окна/уменьшить скорость на одну ступень; при успехе выше 80% в двух сериях предложить усложнение. Иначе сохранить уровень. Это начальная игровая эвристика. Ограничить три ступени, логировать изменения, не менять пороги и калибровку скрыто. Сравнивать результаты только с учётом ступени сложности.

Утомление не диагностировать: после серии ошибок или по запросу предложить отдых, более лёгкий режим или повторную настройку. Покой и отдых не штрафуются. Все предложения доступны двумя каналами. Проверки: адаптация не меняет параметры посреди прыжка; миссии сохраняются; начисление не дублируется при повторе события.

### 18.4. Обработка и ограничение скачков

**[Требование задачи, поток 1]** Помимо сглаживания реализовать явное ограничение резких скачков и настраиваемые dead-zone, порог, длительность удержания и подавление ложных срабатываний. Добавить time-based ограничитель скорости изменения огибающей с настраиваемой крутизной; проверить компромисс между подавлением выброса и пределом 100 мс. Не делать фильтры настолько медленными, что честный сигнал не проходит ограничение задержки. Отдельная диагностика показывает значения до и после обработки.

### 18.5. Баланс времени 60–80% / 20–40%

Исходная задача допускает в остальных 20–40% мини-головоломки, меню, достижения и лор. Метод раздела 11 строже: он исключает меню из знаменателя и проверяет плотность активных уровней. Сохранить этот показатель как внутренний и дополнительно показать разбиение пользовательской сессии: тайминг-зависимая игра, остальные игровые механики, обучение, меню/результаты, технические остановки. Для общего игрового сценария считать доли первых двух категорий; время меню не использовать для искусственного достижения процента. Согласовать знаменатель с экспертами, поскольку исходник не задаёт точного метода измерения. В отчёте явно указать метод, а не объявлять произвольную трактовку официальной.

### 18.6. Встраивание в стороннее приложение

**[Требование задачи, пп. 2–3]** Возможность встраивания и документация интеграции обязательны. Одного IEmgSource недостаточно.

**[Рабочее решение]** Выделить игровой модуль с фасадом `Initialize(config, source)`, `StartSession`, `Pause`, `Resume`, `EndSession`, `Shutdown` и событиями `SessionFinished`, `ProgressChanged`, `Error`. Внешний хост задаёт источник/настройки и получает результат; модуль не завершает процесс приложения, не требует собственного аккаунта и освобождает ресурсы. Имена — внутренний контракт, не SDK устройства.

Для Android подготовить путь Unity as a Library: документировать экспорт, вход/возврат, жизненный цикл, разрешения и ограничения. До сдачи собрать минимальный Android-хост, который запускает модуль, получает результат и возвращается на свой экран. Если такой smoke test не выполнен, указать требование как непроверенное, а не как выполненное благодаря фасаду. iOS-встраивание описывать как будущую работу, если оно не испытано.

Документ `INTEGRATION.md`: зависимости и версии, схема модулей, контракт данных/часов, конфигурация, жизненный цикл, пример вызова и получения результата, ошибки/переподключение, сборка Android-хоста и ограничения.
